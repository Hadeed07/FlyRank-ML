Which web pages will lose Google impressions next month?

A forward-in-time ranking study on a 79-million-row, anonymized search-analytics warehouse. Decision-support, not causal.

1 Abstract2 Problem3 Data4 Method5 Results6 Limitations7 Recommendations8 Reproducibility9 Credit

1. Abstract

This note asks which web pages a content reviewer should open first because their Google search impressions are likely to fall over the next 30 days. It uses a 79-million-row anonymized daily search-analytics warehouse covering 70 clients, restricted to the 42 with enough real history at the decision date. Ninety days of history predict a persistent 30% fall over the following 30 days, using client-grouped validation, a leakage rule for every feature, and a June test month scored after the design was fixed. In June a gradient-boosting model put 98% true declines in its top 50 against a 48% base rate, but a one-line rule (is the last week running below the last month?) ranks as well (AUC 0.75 vs 0.74), and both results come from two adjacent months of a market-wide downturn. The output is a reading order for human reviewers, evidence of persistence rather than cause, and not a basis for automatic changes.

2. The problem

A content team has an afternoon and a portfolio of over a hundred thousand pages. They can open about fifty. Which fifty?

The obvious answer is "the pages whose traffic has been dropping". I tested that rule first (30-day momentum weighted by visibility), and on this data it ranks no better than chance. The useful question turned out to be a different one, and answering it honestly is what this note is about.

The task is framed as ranking, judged by Precision@K: of the K pages a reviewer opens, how many really declined? That matches the decision, because a reviewer reads a list from the top and stops.

Identifiers are pseudonymized hashes, used only for joining and grouping, never as features. This page contains no client names, domains, URLs or queries.

Three things the audit found before any modelling

  • Placeholder rows before real data starts. 933,161 rows across 23 clients sit before the client's search-data start date. All have gsc_data_available = FALSE and zero impressions. A client's usable history starts at its start date, not at its first row.
  • Missing is not zero. Of 20.3 million rows before a client's analytics start date, 5.7 million are flagged FALSE and 14.6 million are NULL, and none are TRUE. "Not measured" is stored two ways, so zero-looking analytics values before that date mean nothing.
  • On real search rows, no row means no impressions. Every real row has at least one impression, so a page with no rows in a window had zero impressions there.

What was excluded, and why

  • Analytics (GA4) features: measured for only part of the panel, and stored inconsistently when missing.
  • The 90-day query table and the last-month sample table: both overlap the label period.
  • Any trend column or last-30-day column computed over the label window.
  • Clients without 90 days of real search history before the decision date and data through the label window. The 34 clients with no daily rows are not covered.
  • Pages with fewer than 100 impressions in the last 30 days of the feature window, so small-number noise cannot create a "decline".

4. Method

Design

One row is one page at one decision date. Features use the 90 days up to the decision date; the label uses the 30 days after it. Two decision dates keep the time order honest.

RoleDecision dateFeature windowLabel window
Train / model selection2026-04-302026-01-31 to 2026-04-30May 2026
Test2026-05-312026-03-03 to 2026-05-31June 2026

The training labels were fully known before the test decision date.

Label

A page declines when its next-30-day impressions are at least 30% below its last 30 days and both 15-day halves of the label window are also below that level, so one quiet week does not count. Base rate: 37.9% (train month), 48.2% (test month).

Features and the leakage rule

A feature is excluded if it computes the label, or if it would not be available at prediction time. Features use impressions, clicks, click-through rate, position, day-to-day volatility, days with impressions, 30-day and 7-day momentum, within-client percentile ranks, and static page properties. Everything is computed from the feature window only.

Scorers

  • Original rule: 30-day momentum drop × visibility. Written before any test result.
  • 7-day run-rate rule: how far the last 7 days run below the last 30 days. Added after the first test result showed the original rule at chance.
  • Logistic regression and gradient boosting, selected with 5-fold cross-validation grouped by client on the train date only.

Uncertainty

Intervals come from resampling clients, not pages, because pages within a client are not independent.

What was fixed before the test, and what was not. The model family, features and label thresholds were fixed on the train date, and the test month was scored once. The diagnostics, the market-adjusted label, the 7-day rule and the threshold sweep were examined on the test month afterwards, so they are exploratory. The 7-day rule is also scored on the train month, where it has no fitting step.

Dropping the 7-day feature takes the model's test AUC from 0.74 to 0.61, so most of what the model uses is one idea: a page whose last week already runs well below its last month is partly already there. That is persistence. It uses only data up to the decision date, so it is legitimate, but it is not a hidden cause the model uncovered.

Why I did not trust the first result

The first rule scored at chance, so "model vs original rule" looked like 0.98 vs 0.48. That comparison flatters the model. I checked three things.

  1. Was June a market-wide dip? Yes. Mean impressions per day across the eligible clients fell from 9.6M (April) to 8.0M (May) to 6.0M (June), so a large share of "declines" is a shared drop.
  1. Does the signal survive subtracting the dip? I redefined the label as "fell 30% more than the client's typical page" (base rate 0.21). The 7-day rule and the model still rank well, and the original rule stays at chance.

The review queue

The model's top 50 over all pages had a Precision@50 of 0.98, but 68% of those pages were new (no impressions in the earlier 60 days of the feature window), though new pages are only 4% of the pool. Those are most likely launch spikes settling, not content needing a refresh. The recommended queue therefore uses established pages only, with at most 25% of the 50 slots for any one client.

6. Limitations and honest framing

Claims here are observed and measured on this panel, directional beyond it, and for decision-support only.

  • Two adjacent months, both in a market-wide downtrend. Nothing here shows the result holds in a flat or growing market. A fair claim needs a re-test in a different regime.
  • The test month was not untouched after the first score. The diagnostics, the adjusted label, the 7-day rule and the threshold sweep were examined there afterwards. The train-month check of the 7-day rule is the independent evidence for it.
  • The model adds little over a one-line rule. Pooled ranking quality is tied in both months; the model led only at the very top of the list in the train month and was indistinguishable in the test month. The honest summary is "a persistence signal ranks next-month declines well".
  • The label is largely persistence, and not causal. It measures a fall in impressions relative to the last 30 days. It does not say why a page fell (ranking loss, demand change, an algorithm update, consolidation, tracking), and nothing here shows that refreshing a page recovers it.
  • Few clients, and they differ a lot. 33 clients in the test month, 21 with enough pages for per-client scores. Decline rates differ widely across clients, so pooled precision partly reflects which clients are in the pool. Intervals resample clients and are wide.
  • Coverage. Only clients with real search history 90 days before the decision date and data through the label window qualify. The 34 clients with no daily rows are not covered.
  • New pages behave differently and need their own treatment.
  • No analytics, keyword grouping, seasonality calendar or consolidation information was used.
  • Small run-to-run variation. Numbers can move in the third decimal between runs because of library versions and threading. This page quotes one saved run.

7. Ranked recommendations

Most important first. These are decision-support recommendations, not causal claims.

  1. Triage with the 7-day run-rate rule. Open the pages whose last 7 days run furthest below their last 30 days. It is transparent and ranks as well as the model on pooled quality.
  2. Check the client before the page. If a client's whole portfolio fell, that is a site-level or market-level event, not fifty content problems. Escalate it once.
  3. Use the established-page queue with the 25% per-client cap.
  4. Review new pages separately. A page that just appeared and is now fading is usually a launch spike settling.
  5. Run the human checklist before acting: did a sibling page absorb the traffic, is it seasonal, did the client's tracking change?
  6. Re-test before automating anything, in a month when the whole panel is flat or growing. Until then, treat the queue as a reading order, not a verdict.
